# 特效制作工作流

## 适用范围

满足任一条件时使用本 workflow：

- 少数简单命令无法稳定完成，需要先理解目标和设计取舍。
- 需求包含风格、节奏、结构、交互或验证方式等未决项。
- 同时涉及对象结构、资源、材质、粒子、脚本、交互或音频中的两项及以上。
- 本轮会改动场景结构、主要资产或交互模式。

切换条件见 `skills_root/SKILL.md` 工作流切换规则表。

## 工作流程

本 workflow 的重点是把效果做出来并验收通过，不应让过程记录抢占执行判断。

1. 按照之前理解用户意图，确认项目目标和交付物。
2. 读取最小必要上下文和规则，确认项目、场景、资源、脚本和约束。
3. 基于用户意图和规则生成 Draft 方案。
4. 对 Draft 方案做规则和意图 Review，补全遗漏和优化
5. 输出 Review 后的方案，按“用户确认闸门”判断是否需要等待用户确认。
6. 用户确认后保存方案，再按“确认后执行”分阶段落地。
7. 当前阶段未通过时，先修当前阶段，不带失败项进入下一阶段。
8. 执行中若必须改变用户可感知效果，回到意图和方案确认。

### 方案 Review 闸门

Draft 方案生成后，执行一次方案 Review，再向用户输出。Review 同时对照用户意图记录和已读取规则：

- 方案目标和交付物是否仍与用户意图一致。
- 是否把 Agent 推断的背景、风格、资产或玩法写成了已确认决策。
- 是否遗漏会影响最终效果的限制、对象层级、坐标体系或验收条件。
- 是否违反 workspace 规则或当前能力边界。

Review 未通过时，先修改方案；不得生成资产、修改工程或保存 confirmed 方案。

## 方案与确认

### 方案输出

发给用户的方案按以下顺序组织，保留“最终效果”和“验收方式”；其余章节及条目按需省略，章节连续编号，不填“无”凑结构。
方案审批以聊天正文为准，必须把 Review 后的方案正文直接发给用户，不得只返回 `design_plan.md`、本地文件路径或文档链接让用户自行打开审批。`design_plan.md` 只作为后台流程留痕和续接依据，默认不向用户暴露该路径。

1. `最终效果`：用一小段概括画面、风格和核心体验。
2. `场景与资产`：先写场景组成，交代主要对象的呈现方式、布局及必要的跟踪、遮挡关系；再列实际需要准备或复用的资产。
3. `交互与状态`：把操作、状态变化和反馈写在一起，覆盖与本轮需求有关的停止、恢复、重置或结束行为。
4. `验收方式`：列出关键验证条件和预期结果，保留可勾选格式。
5. `注意事项`：仅在当前模型不支持图片理解时增加。说明预览截图的视觉验收可靠性受限，并建议用户在确认方案前切换到支持图片理解的模型。

### 方案编写规则

方案围绕用户可感知、可选择、可验收的结果展开。会明显影响最终体验的实现差异，要用具体行为说明。例如，水流是否会被障碍物挡住并改变方向，还是仅表现连续落水和水位上升。无需展开算法、接口或代码结构。

- 最终效果简述主体画面和核心体验，具体交互规则放在“交互与状态”中展开。
- 用户未指定且会明显影响体验的风格、音效或玩法设定，写明“建议”；无法据上下文决定的关键问题，写在对应条目下：`待确认：……`。不默认添加计分、结果页或音频。
- 会收窄用户操作、状态或结果的限制，必须明确写入方案并获确认；未声明或含糊描述的限制不得实现。
- 内部策略不得改变已确认行为；否则先修订方案。
- 场景组成覆盖主要可见对象，包括无需独立素材的动态表现。按需说明位置、前后遮挡、分层及固定或跟踪关系。
- 单个对象无需独立素材时，只写入场景组成；整个方案都无需独立素材时，可省略资产清单。一个对象需要多层素材时，在清单中分别列出，并说明各层用途。
- 资产一项一行，来源写明具体复用对象、内置资源或计划取得方式，不能只写“新增”。提出方案前核实取得方式是否可用；尚未取得的资源标明“待生成”或“待用户提供”。依赖用户文件时，不擅自改为生成资源。
- 水流、水花等动态表现不自动算图片资产；确需贴图、序列帧等资源时，才列入资产清单。
- 验收项写清验证条件、操作和可观察结果，覆盖核心体验及关键边界，避免只把方案描述改成勾选项。
- 按本轮范围填写模板，不适用的条目省略，不为填满模板添加玩法、状态或资源。

### 方案模板

```md
### 1. 最终效果

<用一小段说明主体画面和核心体验。涉及明显影响体验的视觉选择时，写明已确定的选择、建议或待确认问题。>

### 2. 场景与资产

**场景组成**

- <主要可见对象的呈现方式、位置及作用；按需说明摄像头背景、2D / 3D 或固定 / 跟踪关系。>
- <必要的前后遮挡、分层及动态表现；具体触发规则放在“交互与状态”。>

**资产清单**

| 资产 | 来源 | 用途与要求 |
| --- | --- | --- |
| <具体资产及类型> | <具体复用对象、内置资源、待生成或用户提供；尚未取得的用户文件标明待提供> | <使用位置、时机及必要的透明、朝向等要求> |

### 3. 交互与状态

- 初始：<画面与可操作状态>。
- <操作或触发条件> → <状态变化及同步反馈>。
- <与本轮有关的边界或再次体验条件> → <保留、清除或恢复什么>。

### 4. 验收方式

- [ ] <在本轮所需的预览输入或初始状态下>：<可观察的画面、跟踪或遮挡结果>。
- [ ] <执行本轮核心操作或触发过程>：<关键动态变化及反馈>。
- [ ] <验证本轮关键边界或重复操作>：<结束、恢复或重置等预期结果>。

### 5. 注意事项

<仅在当前模型不支持图片理解时保留，说明视觉验收限制并建议切换模型。>
```

### 输出与执行检查

- 输出表格时，每个表头单独成格，表头、分隔行和数据行的列数一致。资产很少时可用列表，保留资产、来源、用途与要求这些信息。
- 资产清单中的每一项，后续都要接入并验证；不再使用的资产应从清单中显式移除。移除会改变已确认的体验时，先说明影响并取得用户确认。

### 用户确认闸门

需要确认方案时，结尾简短邀请用户确认或提出修改，不要求固定回复口令。

方案确认只对用户实际批准的那份方案及其范围有效。默认先在聊天正文中输出当前方案，再等待用户针对该方案明确表达“确认 / 可以 / 开始 / 按这个做”等同意语义，才能执行。对其他方案、此前需求或旧版本的批准，不得用于批准当前新方案；不能仅凭对话里出现过同意词就判定通过。

只有用户主动明确授权“自动审批方案”或“后续方案无需再问我”等含义时，才可在其授权范围内免去逐次确认。普通制作请求、批准某一方案或要求继续执行已批准方案，都不构成自动审批授权。自动审批不免除当前方案正文输出和 Review，也不能代替用户回答影响范围或核心体验的待确认问题。

继续执行同一份已批准且未发生实质变化的方案时，无需重复审批。新需求形成的新方案，或改变原方案范围、核心体验的修订方案，均需重新确认，除非已有明确覆盖本次方案的自动审批授权。

未确认前只能读取必要上下文、输出方案、回答问题和根据用户反馈修改方案。不得调用 `save_plan(status="confirmed")`、`edit_by_dsl`、`generate_assets_batch`、`add_script`、`import_resource`、`set_resource_properties`、`capture_preview`、`interact_by_dsl` 等会改工程、生成资产或验收未落地结果的工具。

当前方案获得明确确认，或满足上述自动审批条件后，立即调用 `save_plan(type="effect", workflow="EffectWorkflow", status="confirmed", ...)`，将确认版计划保存到 `./design_plan.md`，并在计划中记录对应的用户确认或自动审批授权依据及适用范围。未确认方案如需暂存，只能使用非 confirmed 状态，并且不得进入后续执行。
`save_plan` 是后台动作，不替代用户侧方案输出，也不需要作为执行结果专门告知用户；用户需要审批的是聊天正文里的方案，不是工程里的方案文件路径。

### 续接对齐闸门

续接任务时，`design_plan.md` 只是历史方案快照，不是天然有效的执行许可证。进入执行前必须同时满足：

1. 最新用户目标与方案目标一致。
2. `design_plan.md` 覆盖当前实现的关键结构、交互和验收口径。
3. handoff / 当前工程状态没有显示出比方案更新、更具体、且会影响用户感知的实现变化。
4. 能找到用户对这份方案的明确确认依据，或明确覆盖本方案的自动审批授权；方案已经在聊天正文中输出，且之后没有未经批准的实质变化。其他方案的审批记录不能作为依据。

任一条件不满足，都必须重新出方案并等用户确认，不得只凭历史文件里的 `confirmed` 继续执行。

## 方案设计检查

场景、UI、文字、资产接入和验证红线以 `context.workspace.rules/` 为准。本 workflow 只补充完整特效制作需要覆盖的方案决策，不重复展开同一批规则。

| 事项 | 检查内容 |
| --- | --- |
| 场景骨架 | 明确对象、宿主、UI、脚本载体、父子关系、render group 和坐标体系 |
| 体系选择 | 明确 3D / FaceMask / FaceSticker / FaceBinding / HeadTracker / ScreenTransform / VFX 的分工；全脸妆容优先 FaceMask，局部贴纸优先 FaceSticker，3D 面具或挂件才用 HeadTracker；混用时写清转换方式和遮挡顺序 |
| 承载判断 | 区分严格布局玩法和非严格布局玩法；非严格布局默认用独立装饰、局部氛围和独立对象组织画面 |
| 交互热区 | 需要稳定点击、命中、掉落或活动范围时，写清热区和可见表现的关系 |
| 资产计划 | 列出复用和新增资产，写清用途、触发状态、关键约束和验收方式 |
| 用户可见约束 | 所有限制写明边界和触发后的行为；未声明时不得实现 |
| 状态与动态对象 | 按需写清状态触发条件、停止后的保留内容及恢复、结束或重置方式；检查重复出现、移动、销毁或回收对象的来源 |
| 验收方式 | 写用户能理解的验收目标，不把读取规则、查询 schema、确认 GUID 等内部动作写进方案正文 |

## 确认后执行

只有当前方案通过“用户确认闸门”后，才能进入本节。先按“方案设计检查”和工作区全局红线完成执行前检查，再按下面顺序落地。

### 能力路由

具体能力到 skill 的映射见 manifest 的 `routing.capability_map`。

### 阶段推进

用户确认方案后，必须按“执行顺序”生成内部执行 checklist，并分阶段推进。这个 checklist 只约束 Agent 执行，不作为用户确认方案的固定模板。

要求：

1. 每次只推进当前阶段，不要跨阶段提前铺完整场景。
2. 当前阶段未达到通过标准时，先修复当前阶段；不得带着失败项进入下一阶段。
3. 每完成一个阶段，立即更新 `design_plan.md` 中对应 checklist 状态，记录截图、日志、`inspect` 或编译结论等证据。
4. 若阶段执行中发现已确认方案不可达，或必须改变用户可感知效果，按“方案一致性”暂停并请求用户审批；确认并保存新方案后才能继续。
5. 关键路径通过只是中间验收点。除非用户要求停止或出现无法继续的外部阻塞，否则必须继续完成已确认方案中的剩余状态、资产、交互、音频、UI 和验收项。

### 条件式风险探测

- 能力探测默认不执行。
- 仅当现有 Skill、schema 或工程事实无法确认高风险能力可用时，才做最小可逆探测。
- 基础能力、资产验收，以及 Agent 自选路线带来的不确定性，不属于探测范围。
- 探测通过后继续验证关键路径并完成全部方案，不得停在探测结果。

### 执行顺序

| 顺序 | 步骤 | 要做的事 | 通过标准 |
| --- | --- | --- | --- |
| 1 | 确认现状与预览输入 | 读取当前场景、资源、脚本和 Graph 状态；确认要复用的对象、资源和真实 GUID；确认同职能对象是否复用、改名、隐藏或删除；按 `context.workspace.rules/validation.md` 切到匹配效果依赖的预览视频 | 不依赖旧记忆、旧截图或未确认 GUID；创建前知道对象去留，预览视频包含所需部位和动作 |
| 2 | 资产准备 | 列出新增 AIGC 资产清单；预计需要 2 个或更多图片 / 音频资产时，用一次 `generate_assets_batch` 生成本批资产 | 资产状态清楚；生成结果保留 prompt；没有把同一效果所需多项资产拆成多次单项生成 |
| 3 | 搭建骨架 | 创建或复用局部背景、HUD、状态页、动态对象、跟踪父节点和脚本载体；确定 render group 与坐标体系 | 场景树层级清楚、命名正确，没有无意的重复平行结构 |
| 4 | 接入资产 | 逐项绑定图片、花字、音频、Prefab、粒子和材质；不合格资产先重生或停止说明 | `inspect` 显示资源 GUID、尺寸、透明度、层级和组件正确；没有默认图、占位图或未绑定可见对象 |
| 5 | 关键路径验证 | 用最终对象、最终资源和最终脚本先接通一条核心链路，例如开始 -> 命中 -> 反馈 -> 分数变化 | 截图中能看到关键对象和核心反馈；静态绑定与运行态结果都通过；只证明核心链路可用，不代表方案已经完成 |
| 6 | 完成确认方案 | 补齐方案中的全部状态、对象、动画、音频、UI 细节、重置与结束流程，并逐项核对资产表和验收项 | 用户确认的交付内容全部落地；没有待补状态、占位实现、未消费资产或以关键路径代替完整方案的情况 |
| 7 | 脚本验证 | 运行 `run_otsc_check`；用本轮日志确认输入、状态、音频和资源事件 | 编译通过；日志能对应关键交互和状态切换 |
| 8 | 最终验收 | 按“最终验证闭环”验关键状态和关键交互；全部修完后提醒用户保存工程 | 内部执行 checklist 和“验收方式” checklist 都已更新；截图和日志通过；最终回复已提醒用户自行保存工程 |

### 注意事项

- 每完成一个执行阶段，都要同步更新 `design_plan.md` 的内部执行 checklist 和“验收方式” checklist。通过项改为 `[x]`；未通过项保持 `[ ]`，先修复再继续。不要等最终总结时一次性补勾。
- 执行中不得静默偏离已确认方案。若只能做缩水版、伪实现或视觉语义明显不同的替代方案，先暂停并向用户说明差异，得到确认后再继续。
- 任何新增用户可见限制都属于方案变更，必须先修订并确认。
- 会改变场景骨架、跟踪与坐标体系、资产语义、交互或验收口径的实现，不属于等价替换。
- 场景编辑优先 `edit_by_dsl`。已有脚本使用 `edit_by_dsl(edit_script)`；只有新文件才使用 `edit_by_dsl(add_script)`。不要创建 `V2`、`V3` 或 `Final` 等平行脚本。
- 调整对象层级、移动对象到新父节点或重排 render group 后，必须马上用 `get_scene` 检查结构是否收敛。
- 不要通过复制同职责对象来绕过遮挡、绑定或排序问题；确需创建替代对象时，验证通过后必须删除、隐藏或解绑旧对象。
- 每完成一个逻辑关注点，都按“静态绑定检查 -> 运行态截图”的顺序验证。静态绑定不正确、可见 Image 的 texture 与资产清单不一致，或文字 / 图标 / 反馈没有挂到对应底板、面板、按钮下时，先修父子关系和排序，不进入预览试错。
- 游戏或多状态脚本记录关键交互、状态切换、资源事件和 guard；音频记录 `play()`、`pause()`、`resume()`、`stop()`、完成态和缺绑。日志前缀优先使用 `[input]`、`[state]`、`[audio]`、`[guard]`。
- 最终总结必须对照已确认方案交代完成度。凡是实现路线、资产语义、3D / 2D 体系、跟踪方式、音频或交互与方案不一致，即使截图和编译通过，也必须明确列出偏差、原因和影响。

## 反模式与路由恢复

反模式自查和路由失败恢复流程见 `context.workspace.rules/anti-patterns.md`。每次编辑前和连续失败时按该文件执行。

## 最终验证闭环

整体完成后，按工作区全局验证规则执行视觉和功能验收。本 workflow 的最终验证只覆盖已确认方案中的关键交互、关键状态和新接入的高风险能力。

推荐顺序：编译检查 -> 初始态截图 -> 一次核心交互截图 -> 一个非初始状态直达截图 -> 本轮日志。每张截图都要人工看图；失败先修复并回到当前步骤重验。

特别注意：

- 验收必须回写 `design_plan.md` 的 checklist。每个验证项都要补充截图结论、日志结论、检查到的对象 / 资源状态或失败原因。
- 静态结果用 `capture_preview`；动态和交互结果按 `context.workspace.rules/validation.md`，在 `interact_by_dsl` 中从 `reset_preview` 开始，进入明确起始状态、触发交互并分时 `screenshot`。临时属性跳转后也在当前运行态截图，不再重载。
- 快速状态跳转、短生命周期反馈和临时隐藏对象的恢复方式均按验证规则执行；核心交互必须另从真实入口验证，不能只凭跳转后的画面判定通过。
- 工程发生实际改动后至少完成一轮重载后的截图验证，可以是静态截图或动态、交互截图序列。
- 本 workflow 不调用 `save_project`。最终验证完成后，在最终回复中明确提醒用户自行保存工程。

## 停止条件

- 用户已明确确认方案或关键实现路径；未确认时只能停止在方案输出或澄清阶段。
- 结果已落到当前工程，而不只停留在素材层。
- 已确认方案中的交付项和验收项均已闭环；关键路径通过不能作为提前结束任务的依据。
- 已完成至少一轮可解释的预览验证。
- 涉及脚本时，`run_otsc_check` 通过，或错误已明确记录。
- 最终回复已提醒用户自行保存工程。
